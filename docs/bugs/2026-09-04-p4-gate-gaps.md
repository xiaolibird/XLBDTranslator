## ① bash 门对 `rm` / `git clean` 完全不设防，而 `results/` 不在版本控制内

**实测证据**

`scripts/hooks/pre_bash.sh:15` 的相关性预筛：

```bash
printf '%s' "$PAYLOAD" | tr -d "'\"\\\\" | grep -qiE 'experiments|pipeline|p4_card|p4_py|python|\.py|export|declare|typeset|set -a'
```

正则**不含** `rm` / `git clean` / `git checkout` / `git stash` / `mv`。不匹配即 `exit 0` 完全不进门。`_gate_bash.py` 的全部职责是「找到 python 启动 + 回看卡绑定」，无破坏性命令识别。

`.gitignore:16` 是 `/results/*`（仅 `figures/` 与 `README.md` 例外）。实测：

```
$ git ls-files results/paper1_crosscenter/mnn_deploy/ | wc -l
0
```

而该目录下 47 个文件是 done 卡 `X-2026-09-02-05` 与三条 answered RQ 的**全部证据**。`idd_leakage/`（992K）同理，且 `native`/`fallback` 两臂是从它现读的——它没了，`mnn_deploy` 也重建不出来。

**已做的临时缓解**：2026-09-03 落了仓库外快照 `~/Desktop/Lab/P4_results_snapshot_2026-09-03/`（1.2M，含两个目录）。**这不是修复**，只是这一次的保险。

**建议**：预筛正则加破坏性动词；或更省事——给 `results/` 加一条定期快照（cron 或 pre-commit hook），因为它在设计上就注定不进 git。

## ② 写门放行、commit 才红，而"修复"动作会篡改预注册

**实测证据**

场景：把 `RQ-2026-09-01-02` 里被禁的短语「文献主流做法」全局替换。该短语共 **5 处**：

| 行 | 位置 | 是否冻结 |
|---|---|---|
| `:9` | `hypothesis` | 否 |
| **`:26`** | **`criteria[C10].rationale`** | **是**（`criteria` ∈ `RQ_STAMP_KEYS`） |
| `:42` | `answer_statement` | 否 |
| `:72` / `:75` | 正文散文 | 否 |

- 写门 `scripts/hooks/_dry_run_write.py` 只对单文件跑 `check_prd --dry-run`（schema 层），全局替换后实测 **0 findings, exit 0 —— 放行**。
- 直到 commit 时 `ci.sh` 步骤 5.5 的全量 `check_prd` 才报 **2 条 hard `PREREG-DRIFT`**（`X-2026-09-02-01` 与 `-02` 的 run 记录里的 `rq_prereg_hash` 与现值不符），exit 1。

**为什么这比"红一次"更糟**：agent 面对 PREREG-DRIFT 最自然的修法是**重 stamp** —— 而那会另触「prereg_hash was re-stamped AFTER」，并且把一个**已 answered、已被两张 done 卡的 provenance 锚定的预注册哈希**改掉。数据还在，但预注册的可信度没了。这是本次审出的唯一一条"看起来像修复、实为不可逆损害"的路径。

**建议**：写门在 dry-run 之外，对 `docs/prd/RQ-*.md` 的改动额外比一次 `rq_prereg_hash`（改前 vs 改后），变了就当场 deny 并提示"你动的是冻结键"。这比等到 commit 再红要早得多，也堵死了重 stamp 那条歧路。

## ③ 测试用子串匹配路由驱动

**实测证据**：`tests/test_mnn_line.py`

```python
:198    drv = next((s for name, s in drivers.items() if name in art), None)
:249    fam = next((v for k, v in fams.items() if k in art), None)
```

两处都是 `if <name> in <artifact路径>` 的子串匹配 + `next()` 取首个命中。新驱动若命名为 `mnn_deploy_normal`（artifact 路径含 `mnn_deploy_normal/summary.json`），会**先命中已有的 `mnn_deploy`**，于是拿去 `mnn_deploy.py` 的源码里找新键——必然找不到，测试红，而报错指向的是错误的文件。

**规避办法（若暂不修）**：新驱动名不得以既有驱动名为前缀；或在 `drivers`/`fams` 字典里把长名排在短名之前（依赖 dict 插入序，脆）。

**建议**：改为精确前缀匹配（`art.startswith(name + "/")` 或按 artifact 的第一段路径查表）。

## ④ `citl` 的优化边界静默截断

**实测证据**：`src/p4/core/clinical_metrics.py:145`

```python
out["citl"] = float(minimize_scalar(nll, bounds=(-10, 10), method="bounded").x)
```

`method="bounded"` 在真优点落在 [−10, 10] 之外时**返回边界值本身**，不抛异常、无 assert、无 warning。同文件 `:291` 另有一处 `bounds=(-20, 20)`，同样问题。

现有产物里最大 |citl| 是 1.013，尚安全。但任何**系统性平移**的臂（例如把整列输入按临床正常值常数填充）都可能把 CITL 推到边界外，那时读到的 ±10 是**假值冒充有效值**。

**建议**：加一条 `assert abs(x) < bound - eps`，或返回时带一个 `citl_at_bound: bool` 标志供上游门检查。

## ⑤ `evaluate()` 丢弃已算出的指标，而它是六个驱动的共享入口

**实测证据**：`src/p4/baselines/imputation_validation.py` 的 `evaluate()` 返回**恰好 7 键**：

```python
return {"auroc": ..., "cal_slope": cal["cal_slope"], "sbrier": cal["brier_skill"],
        "nb10": ..., "nb20": ..., "n": ..., "prevalence": ...}
```

而它调用的 `calibration()` 已经算出并被丢弃的有：`brier`(:113)、`cal_intercept`(:127)、`citl`(:145)、`ece`(:160)。

**为什么不能"顺手加回来"**：`evaluate` 被 6 个驱动 + 2 个测试共用（`idd_leakage` / `mnn_deploy` / `mnn_dial` / `mnn_native_fill` / `mnn_selfmask_sig` / `paper1_synth` 两个 + `tests/test_{mnn,idd}_line.py`）。加键会让 `mnn_deploy.py::repro_check` 的 keyset 断言对**全部 22 格**失败（盘上参照 dict 只有 7 键），并改写已 done 卡的产物 schema。

**后果**：任何想报 CITL/ECE 的新分析，都只能在新驱动里**自己再调一次** `clinical_metrics.calibration(y, p)["citl"]`——本次 v1.3 批注就是这么写死的。这是可行的，但意味着**同一份预测被算两遍校准**，且新旧口径有分叉风险。

**建议**：给 `evaluate` 加一个 `extra: tuple[str,...] = ()` 参数，默认返回现有 7 键（旧驱动零影响），新驱动按需 `evaluate(y, p, extra=("citl","ece"))`。这样既不动既有 schema，也不必重复计算。
